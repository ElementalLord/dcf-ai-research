# Demand-driven question resolution and admission

Ask resolves conversational references and selected personality IDs with the existing query context code. Existing `retrieveEvidence` then uses the indexed Supabase lexical search, approved claims, passages, and bounded semantic fallback. The new `resolveQuestion` service is the single local-evidence decision before Google grounding or the existing approved-source/Brave fallback. It performs no external I/O or database writes.

The resolver admits only evidence tied to the exact selected personality ID. Claims must pass the active approval-origin policy, have approved review status and provenance, and have a supported epistemic contract when one exists. Approved passages must be readable and any live cache entry must be unexpired. Traditional narratives do not establish dated historical facts. The existing sufficiency assessment checks concept, lens, context, breadth, and comparison coverage; explicit factual requirements add date, contribution, significance, comparison, contestation, and current-observation checks. A local answer is routed without external search only when every requirement is covered. Retrieval errors block external research.

Each result includes a stable SHA-256 `needId` over personality UUID, normalized topic, intent, lens, and context. Each missing requirement has a stable gap ID, type, suitable source classes, and completion condition. The IDs are deterministic hints for future coordination, not assertions that semantic equivalence has been proved. Prompt 2 should accept `EvidenceGapRequest` from `src/lib/ask/question-resolution.ts`, honor `maxExternalSearches`, use `existingEvidenceIds`, and return independently verified passages or a bounded failure. It should never treat an answer-cache entry as evidence. The existing answer cache remains a synthesis optimization only.

Stage 1 needed no migration. Stage 2 adds `demand_research_needs` and two service-role-only RPCs in `20261018010000_demand_research_needs.sql`. The row is keyed by a stable hash of `needId` plus gap IDs, so paraphrases share work while changed gaps can start a new attempt. A database lease suppresses concurrent paid searches across serverless instances. It stores status, usage counts, retry time, and failure category only. It does not store search results, extracted text, or user questions. A missing migration fails closed before any external search. The migration is committed but has **not** been applied to the live database.

## Stage 2 on-demand research

Set `DEMAND_RESEARCH_ENABLED=true` after applying the migration to use `executeDemandResearch` from `src/lib/live-research/on-demand-engine.ts`. With the flag unset, the existing Ask fallback remains available. In the new path, Ask calls the engine only when the resolver returns a non-null `researchRequest`; it never invokes the older Google or Brave fallback as a second search. One Ask request shares one Brave search allocation even when up to three personalities are selected. The engine plans one gap-specific query using the existing research planner, calls Brave at most once, inspects at most eight candidates, and reads at most four original sources. Provider snippets are never evidence. Source fetches reuse the repository's bounded HTTPS, DNS/redirect and extraction controls; the new path also checks robots rules before reading. A recognizable publisher alone is insufficient: the original document must identify the subject and contain a directly relevant passage.

`OnDemandResearchResult` contains `requestId` (attempt), `needId` (original information need), `workId` (gap-specific coordination), status, candidate decisions, source identities, passages with real locators when available, potential contradiction flags, unresolved gaps, and search/fetch/model usage. A retrieved passage enters Ask as `brave_live` with `sourceStatus: "discovered"`; existing prompt and citation code explicitly labels it as live research, not Mentor-approved knowledge. If research fails or the budget is exhausted, Ask can use valid partial local evidence but cannot present the missing fact as established. No stage 2 path writes claims or changes approval records.

The stage 3 input is `ResearchFinding[]` plus the original `EvidenceGapRequest`. Each finding has `source` (`url`, underlying `workKey`, DOI/ISBN, author, publisher, publication date, existing approved `sourceId` if any, retrieval time, provenance completeness), `passage` (bounded text, source locator, support level and reason), `relation` (`supports` or `potential_contradiction`), `retention` (`transient_only` or `license_candidate`), `rightsDeclaration`, `citeableNow`, and `verificationReady`. `license_candidate` records an explicit metadata signal, not permission or approval by itself. Distinct URLs with the same DOI or underlying work key are one source family.

## Stage 3 verification and admission

`verifyDemandKnowledge` in `src/lib/live-research/knowledge-verification.ts` runs only after question-triggered research returns original-source findings. It extracts at most four atomic propositions in one bounded model call, then checks each against its original passages in at most one separate entailment call. The verifier checks exact entity, dates and units, qualifiers, source independence, equivalence and conflicts with approved claims. Model confidence never substitutes for documentary support. Date and numeric values must also appear literally in a supporting passage. A quotation without a validated exact span, priority/causal/impact assertion, uncertain statement, traditional narrative, interpretation, and contested claim are quarantined; a source that contradicts or fails identity may be rejected. A missing provider or database check fails closed. No further web search occurs.

The automatic publication class is deliberately narrow: a routine historical fact with strong support in two genuinely independent historical/scholarly works under the existing `HISTORICAL_FACT` contract, or an exact simple award/appointment fact from the issuing body's own official record. The latter is a specific one-source exception; it does not relax the general contract. The epistemic taxonomy also distinguishes contemporary observations, scientific priority, and causal significance; these are evaluated but quarantined under this version. The document verifier must confirm documentary independence or issuing authority, as applicable. Existing approved claims are checked for equivalent wording, paraphrases, competing dates/quantities and material contradictions. Conflicts remain quarantined and never overwrite human or Mentor decisions.

Permanent passage storage requires complete bibliographic identity, HTTPS, a stable locator, and an explicit public-domain or Creative Commons declaration from the original document. A vague “open access” label is insufficient. Only a 240-character supporting excerpt, bibliographic source and independently worded claim are retained. Search-result content and full copyrighted documents are never admitted by this path. Nonadmitted decisions store hashes, outcomes and reason codes, rather than untrusted source prose.

`20261018020000_demand_verified_admission.sql` adds a service-role-only decision ledger, a distinct `automated_evidence_verification` origin, and an atomic RPC. That single transaction checks the payload and existing identity, inserts the claim, source, passage, links, epistemic contract and decision, or rolls back all publication. An advisory lock and admitted identity index make repeated admission idempotent. The approved claim enters the existing retrieval path in both strict and test policies only after commit; it is never labeled Mentor-approved. Suspension deactivates its exclusive passage. Ask recomputes its evidence-signed answer-cache key from current retrieval, so a suspended claim cannot keep an old answer valid. Existing Ask sufficiency gates still apply.

Both `DEMAND_AUTO_ADMISSION_ENABLED` and `DEMAND_VERIFICATION_SHADOW_ENABLED` default to false and are independent from `DEMAND_RESEARCH_ENABLED`. Shadow mode evaluates and records decisions without publishing claims. Enable research only after its migration; apply this second migration before enabling shadow or admission; then validate with fixtures and monitored requests before enabling `DEMAND_AUTO_ADMISSION_ENABLED`. Neither migration has been applied to the live database in this work. If admission fails, Ask may still cite suitably labeled live evidence for the current response, but the claim is not reported as saved. Stage 4 can add fuller cost controls, policy telemetry, and production integration.

## Provider and retention boundary

The new service uses Brave results transiently to locate sources, calls the original publisher, and never persists Brave titles, snippets, or result lists. The existing general Brave cache is bypassed by default unless `BRAVE_SEARCH_STORAGE_RIGHTS=true` documents an account with storage rights. The new service does not use Gemini grounding links for acquisition. This follows [Brave's Search API terms](https://api-dashboard.search.brave.com/documentation/resources/terms-of-service) and [Gemini API grounding terms](https://ai.google.dev/gemini-api/terms.md), reviewed 2026-10-18. Original-source passages remain request-scoped. Explicit open-license or public-domain metadata marks a *candidate* for Prompt 3 retention review; uncertain rights remain transient. No complete third-party document is saved by this engine. Source access, copyright and licensing still require source-specific checks before permanent ingestion.

The feature remains on the development branch. Applying the migration and enabling the flag are separate rollout steps; neither is part of this stage's code commit. The legacy Google-grounding path remains outside the new engine and should be reviewed before any future attempt to use its results for permanent acquisition.
