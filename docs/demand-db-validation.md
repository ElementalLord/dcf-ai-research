# Demand database release validation

The automated integration suite in `tests/corpus/demand-local-db.test.ts` runs against a **loopback Supabase API only**. It uses mocked search and verification providers, but real PostgreSQL tables, RPCs, constraints, RLS, and PostgREST roles. It refuses to run against a non-loopback API URL. Do not commit schema exports, database URLs, or local Supabase keys.

## Prepare an isolated database

1. Start Docker. Create a fresh temporary Supabase project outside this repository with `supabase init --workdir /tmp/dcf-demand-validation --yes`, then `supabase start --workdir /tmp/dcf-demand-validation`. This does not use or alter the repository's linked project.
2. Obtain a **schema-only** export of the pre-demand DCF `public` schema from an authorized read-only connection. For example, load a protected local environment file containing `DCF_SCHEMA_DATABASE_URL`, then run `supabase db dump --db-url "$DCF_SCHEMA_DATABASE_URL" --schema public --file /tmp/dcf-pre-demand-schema.sql`. Disable shell tracing; keep the file mode `0600`. Verify that it contains core tables and no `COPY` or `INSERT` data statements. Never run remote migration, reset, or data-export commands.
3. In the disposable local database only, create the existing `vector` extension in `extensions`, then restore the export with `psql -X -v ON_ERROR_STOP=1 --single-transaction`. Apply `20261018010000_demand_research_needs.sql`, `20261018020000_demand_verified_admission.sql`, and `20261018030000_demand_budget_and_activity.sql` in order, each with `ON_ERROR_STOP=1` and its own transaction. The local Supabase database container is named `supabase_db_<temporary-project-id>`; `docker exec -i` can stream each file to `psql` without copying secrets into the repository.
4. Save `supabase status --workdir /tmp/dcf-demand-validation -o env` to a mode `0600` file outside the repository. Load that file without printing it, export `NEXT_PUBLIC_SUPABASE_URL=$API_URL`, `SUPABASE_SERVICE_ROLE_KEY=$SERVICE_ROLE_KEY`, `DCF_LOCAL_ANON_KEY=$ANON_KEY`, `DCF_LOCAL_JWT_SECRET=$JWT_SECRET`, `DCF_LOCAL_DB_VALIDATION=true`, `EMBEDDINGS_DISABLED=true`, `SYNTHESIS_DISABLED=true`, and `EVIDENCE_POLICY_MODE=strict`. Run `npx vitest run tests/corpus/demand-local-db.test.ts` with local loopback access.

The suite creates fictional personalities and evidence only in the disposable database. It verifies one search across simultaneous equivalent requests, automatic admission, real Ask retrieval and reuse, provenance relationships, mid-transaction rollback, idempotent concurrent admission, rights rejection, negative verification, suspension, RLS/role denial, emergency admission pause, stale leases, cooldowns, and concurrent, daily, and monthly spending limits. It does not use paid providers. Stop the temporary Supabase project when done; do not use `supabase stop --all` or remove unrelated Docker volumes.

## 2026-10-18 result

A schema-only export from the authorized existing DCF connection was restored into a disposable local Supabase PostgreSQL 17.6 database. The export had no table rows and no demand tables. All three demand migrations applied in order on a fresh local stack. Five real-database integration cases passed. The admission function required two targeted SQL corrections: parenthesizing JSON extraction before citation concatenation, and mapping evidence taxonomy values to the existing `sources.source_type` constraint. The date-intent rule was narrowed so “What year…” can reuse an admitted dated fact without demanding unrelated historical-setting evidence. These fixes do not change admission eligibility or source-rights rules.
